How SAM actually deploys

The conversion from SAM to CloudFormation does not happen on your machine. Knowing exactly where it happens explains most of what else is confusing about this pipeline.

The one thing worth internalising

local vs. remote — where the template changes shape

Running sam build on the FinEvents template produced .aws-sam/build/template.yaml. That file still declares Type: AWS::Serverless::Function and still carries Transform: AWS::Serverless-2016-10-31 at the top. Nothing was converted.

SAM is a CloudFormation macro. The expansion runs inside AWS, after your template has been uploaded. The SAM CLI's job is to get the template and the code there — not to translate them.

  1. 01

    Author local

    You write template.yaml. Globals, Conditions and !If are all still unresolved text at this point.

  2. 02

    sam build local

    Copies each function's source into .aws-sam/build/<LogicalId>/ and points CodeUri there. Where a requirements.txt exists, dependencies install into that directory for the target runtime and architecture.

  3. 03

    sam deploy, packaging half local

    Zips the build directory, uploads it to S3, and rewrites CodeUri to the object URI. CloudFormation cannot read your disk, so the code must be in S3 before the API call — that is the entire reason the artifact bucket exists.

  4. 04

    The transform in aws

    CloudFormation sees the Transform declaration and runs the macro. AWS::Serverless::Function becomes AWS::Lambda::Function; Globals flattens into every function. Resources you wrote natively — the log group, the IAM role — pass through untouched.

  5. 05

    Changeset in aws

    A diff between desired and current state. Nothing exists yet. This is also where CAPABILITY_NAMED_IAM is enforced: a role with a name you chose could shadow an existing one, so AWS demands explicit consent rather than inferring it.

  6. 06

    Execute in aws

    CloudFormation builds a dependency graph from your intrinsic functions — not from file order. HelloFn references !GetAtt HelloFnRole.Arn, so the role provisions first; the log group has no references and goes in parallel. !Sub, !Ref and !If all resolve here.

Rollback is not deletion. A failed update reverts to the last good state automatically. A failed first create has no good state to return to, so you get ROLLBACK_COMPLETE — a zombie stack that blocks retrying under the same name until you delete it. That is the one you are most likely to meet.

Side by side

the same infrastructure, written both ways

SAM is a superset of CloudFormation — every valid CloudFormation template is a valid SAM template, and your own template.yaml mixes both freely. So the question is only what the shorthand saves. Three cases, in ascending order of how much it matters.

1 · Shared defaults across every function

FinEvents will run roughly fifteen Lambdas, all on the same runtime and architecture. CloudFormation has no inheritance mechanism at all.

SAM declared once 
Globals:
  Function:
    Runtime: python3.13
    Architectures: [arm64]
    Timeout: 10
    MemorySize: 128
    Environment:
      Variables:
        FINEVENTS_ENV: !Ref Environment

# every function inherits all of it
CloudFormation × 15 functions 
IngestFn:
  Properties:
    Runtime: python3.13
    Architectures: [arm64]
    Timeout: 10
    # …and 3 more lines

ClassifyFn:
  Properties:
    Runtime: python3.13   # again
    # …and 13 more functions
Failure mode →

Drift. One function quietly ends up on a different runtime or memory size, and nothing tells you. With Globals that divergence is impossible to express by accident.

2 · A scheduled function — the FinEvents daily run

One Events block versus three hand-wired resources. This is T11.4, so it is the case you will actually hit next.

SAM 1 resource · 10 lines 
DailyRunFn:
  Type: AWS::Serverless::Function
  Properties:
    CodeUri: src/lambda/daily/
    Handler: app.handler
    Events:
      Nightly:
        Type: Schedule
        Properties:
          Schedule: cron(0 21 ? * MON-FRI *)
CloudFormation 3 resources · 28 lines 
DailyRunFn:
  Type: AWS::Lambda::Function
  Properties:
    Code:
      S3Bucket: !Ref ArtifactBucket  # you
      S3Key: daily/9f2c1b.zip        # wire
    Handler: app.handler             # these
    Runtime: python3.13
    Role: !GetAtt DailyRunFnRole.Arn

NightlyRule:
  Type: AWS::Events::Rule
  Properties:
    ScheduleExpression: cron(0 21 ? * MON-FRI *)
    State: ENABLED
    Targets:
      - Arn: !GetAtt DailyRunFn.Arn
        Id: DailyRunTarget

NightlyInvokePermission:
  Type: AWS::Lambda::Permission
  Properties:
    FunctionName: !GetAtt DailyRunFn.Arn
    Action: lambda:InvokeFunction
    Principal: events.amazonaws.com
    SourceArn: !GetAtt NightlyRule.Arn
Failure mode →

Forget the Lambda::Permission and the schedule fires into a wall — EventBridge logs failed invocations and the function never runs. Nothing in the template is invalid, so deployment succeeds and the daily run silently doesn't happen. Under forward-only, a missed day cannot be re-run.

3 · An HTTP endpoint — the api/ module

The widest gap. Four lines of Events expand into a full API Gateway REST stack.

SAM 1 resource · 10 lines 
PredictionsFn:
  Type: AWS::Serverless::Function
  Properties:
    CodeUri: src/lambda/api/
    Handler: app.handler
    Events:
      Get:
        Type: Api
        Properties:
          Path: /predictions/{instrument}
          Method: get
CloudFormation 7 resources · ~70 lines 
# each written out in full:

AWS::Lambda::Function
AWS::ApiGateway::RestApi
AWS::ApiGateway::Resource      # /predictions
AWS::ApiGateway::Resource      # /{instrument}
AWS::ApiGateway::Method        # + integration URI
AWS::ApiGateway::Deployment    # DependsOn: Method
AWS::ApiGateway::Stage
AWS::Lambda::Permission

# plus the integration ARN, hand-built
# with !Sub across region + account
Failure mode →

Omit DependsOn on the Deployment and CloudFormation may create it before the method exists — you get a deployed API with no routes, and a 403 that looks like an auth problem. It is the single most-reported CloudFormation footgun, and SAM removes the opportunity to make it.

The fourth difference, which isn't in the template at all

CodeUri: src/lambda/hello/ is a path on your disk. Raw CloudFormation only accepts Code: {S3Bucket, S3Key}, so you own the whole pipeline: build the zip with wheels for the target platform, upload it, and compute a key that changes whenever the content does.

That last part bites hardest. Reuse the same S3Key and CloudFormation sees no diff, reports a successful deploy, and leaves the old code running. Your change simply doesn't ship. sam build and sam deploy hash the artifact and rewrite the key for you — which is also why they cross-compile correctly for arm64 from a Windows x86 host.

Every one of these failure modes is silent: a successful deploy that doesn't do what you wrote. That's the real argument for SAM over raw CloudFormation — not fewer lines, but fewer places to be quietly wrong.

Where SAM earns nothing

In template.yaml as it stands today. One function, an explicit role, no Events, and a Globals block serving a single function — converting it to raw CloudFormation would cost about ten extra lines. Right now the value is entirely sam build and sam local invoke. The template shorthand starts paying at T11.4.

Is SAM cloud-agnostic?

short answer: no — but the question hides a better one

SAM is AWS-bound at every layer. It is a macro for CloudFormation, which is an AWS service; every resource type is AWS::*; and the CLI speaks only to CloudFormation. There is no Azure or GCP mode, and there is no plan for one.

But "which IaC tool" is the least important portability decision you will make. Here is the landscape, with what each one actually buys:

ToolPortable?What that means in practice
AWS SAM AWS only A CloudFormation macro. Shorthand for serverless resources — that is its whole scope.
CloudFormation AWS only The engine underneath. SAM, CDK and Amplify all end up here.
AWS CDK AWS only Real languages, but it synthesises to CloudFormation. The sibling projects CDKTF and cdk8s target other backends; AWS CDK itself does not.
ARM / Bicep Azure only Azure's equivalent of CloudFormation, with Bicep as its SAM-like shorthand.
Terraform / OpenTofu tool, not config One language and one workflow across every provider — but you still write aws_lambda_function or azurerm_linux_function_app. Your skill transfers; your code does not.
Pulumi tool, not config Same bargain as Terraform, expressed in general-purpose languages.
Crossplane tool, not config Same again, driven through Kubernetes. Adds a control plane you now have to run.
Serverless Framework nominally multi Advertises several providers; AWS is the only first-class one in practice.

No mainstream IaC tool gives you portable configuration. They give you a portable language over provider-specific resources. Moving clouds means rewriting the resource definitions either way — Terraform just spares you learning a second syntax while you do it.

What lock-in actually costs FinEvents

Close to nothing extra, because the binding decisions were made above the IaC layer. This pipeline runs on Bedrock (Nova Lite, Pro and Premier), AgentCore Runtime, Step Functions, DynamoDB and Athena. None of those has a drop-in equivalent on Azure or GCP — the model IDs alone are AWS-specific, and ADR-0027 already treats them as configuration precisely because they change.

Rewriting template.yaml in Terraform would produce a portable dialect describing an unportable architecture. The honest reading is that SAM costs you a syntax you would have to abandon anyway, and buys a shorter template plus first-class local invocation. That trade is why ADR-0015 chose it.

When you would reach for Terraform instead

Three conditions, none of which hold here today: you are provisioning across more than one cloud and want one workflow; you need resources CloudFormation supports late or not at all; or your team already knows HCL and the switching cost is negative. Multi-cloud ambition is not on that list — portability you never exercise is a cost you pay every day for a benefit you never collect.
